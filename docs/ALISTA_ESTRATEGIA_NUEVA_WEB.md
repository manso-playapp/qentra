# ALISTA — ESTRATEGIA Y ARQUITECTURA DE LA NUEVA WEB
## Documento base para UX/UI, narrativa, contenido y desarrollo

**Fecha:** 24 de agosto de 2026  
**Estado:** Base estratégica para rediseño completo de la web  
**Mercado de entrada:** Cumpleaños de 15  
**Objetivo:** convertir la web en una herramienta de venta, demostración de producto y construcción de marca.

---

# 0. Propósito de este documento

Este archivo define cómo debe construirse la nueva web pública de Alista.

Debe ser utilizado como contexto transversal para:

- estrategia de comunicación;
- UX;
- UI;
- copy;
- motion;
- desarrollo frontend;
- selección de imágenes y video;
- demostraciones de producto;
- conversión;
- campañas;
- landings;
- piezas comerciales.

La web anterior basada en Qentra puede servir como referencia técnica, pero **no debe tomarse como referencia estratégica de comunicación**.

La nueva web no debe limitarse a reemplazar el nombre Qentra por Alista.

Debe cambiar su lógica comercial completa.

---

# 1. Decisión de mercado

## DECISIÓN CERRADA

Alista saldrá inicialmente al mercado como una plataforma especializada en **cumpleaños de 15**.

La tecnología puede conservar capacidad de expansión futura, pero:

> **el producto percibido, la comunicación y la web deben hablar desde el mundo de los 15.**

No presentar Alista inicialmente como:

- plataforma para todo tipo de eventos;
- guest experience platform genérica;
- software corporativo de eventos;
- herramienta universal de check-in.

La especialización es una ventaja.

---

# 2. Qué debe vender la web

La web no debe vender:

- software;
- QR;
- una invitación digital;
- un dashboard;
- un sistema de listas.

Debe vender una transformación:

> **Pasar de organizar una fiesta entre mensajes, listas, dudas y cambios a sentir que todo está preparado.**

El producto se demuestra mediante:

> invitación → confirmación → conocimiento → organización → personalización → pago cuando corresponde → preparación → llegada.

---

# 3. Tesis de la web

> **La fiesta dura una noche. Prepararla empieza mucho antes.**

La web debe hacer visible que la experiencia que se vive esa noche depende de muchas cosas que fueron resueltas antes.

Alista ocupa ese territorio.

---

# 4. A quién le habla

La web debe poder convertir dos grandes audiencias sin intentar escribir todo para ambas al mismo tiempo.

## 4.1 B2C — Familia / quinceañera

Busca:

- tranquilidad;
- orden;
- identidad;
- facilidad;
- menos mensajes dispersos;
- saber quién viene;
- cobrar entradas si corresponde;
- preparar la llegada.

## 4.2 B2B2C — Planner / salón / productora

Busca:

- recurrencia;
- profesionalización;
- autonomía;
- menos errores;
- mejor servicio;
- herramienta reutilizable;
- diferenciación comercial.

## Regla

La home vende la idea general.

Después se abren dos recorridos:

### Estoy organizando mis 15

### Organizo fiestas de 15

---

# 5. Héroe narrativo

El anfitrión sigue siendo el héroe emocional.

Pero el comprador no siempre es el anfitrión.

## Roles

- **Comprador:** familia o profesional.
- **Usuario operativo:** familia, planner, equipo.
- **Héroe narrativo:** quinceañera / anfitrión.
- **Beneficiario final:** invitado.

La web debe vender preparación y demostrar operación antes de cerrar con emoción.

---

# 6. Jerarquía de comunicación

## Regla principal

> **Primero resolvemos la operación. Después mostramos lo que esa resolución permite vivir.**

Orden recomendado:

1. problema real;
2. mecanismo de Alista;
3. resultado concreto;
4. beneficio emocional.

Evitar comenzar con mensajes emocionales genéricos sin demostrar valor.

---

# 7. Dirección visual

La web no debe parecer:

- SaaS genérico;
- fintech;
- software corporativo frío;
- invitación de princesa;
- cotillón;
- web de salón;
- landing genérica de eventos.

Debe sentirse:

- joven;
- premium;
- editorial;
- contemporánea;
- humana;
- tecnológica sin parecer técnica;
- festiva sin ser infantil;
- emocional sin cursilería.

## Mezcla recomendada

> **Editorial de moda + experiencia digital + evento contemporáneo + producto SaaS serio.**

---

# 8. Video real en el hero

Existe material audiovisual real del cumpleaños de Dharma.

Debe evaluarse como material principal del hero.

## Usarlo si muestra

- personas reales;
- energía;
- llegada;
- fiesta;
- emoción;
- escala;
- autenticidad;
- recepción;
- interacción.

No debe funcionar como fondo decorativo.

Debe sostener la tesis:

> **Lo que se vivió esa noche fue posible porque muchas cosas estuvieron preparadas antes.**

---

# 9. Hero recomendado

## Headline principal

> **Tus 15 empiezan mucho antes de esa noche.**

## Bajada

> Invitaciones, confirmaciones, grupos, entradas y accesos. Todo preparado en un solo lugar.

## CTA principal

> **Quiero Alista en mis 15**

## CTA secundario

> **Soy planner o salón**

## Criterio

El visitante debe entender en menos de un viewport:

- que es para 15;
- que no es solo una invitación;
- que Alista prepara la experiencia;
- que existe una solución profesional detrás.

---

# 10. Primera transición narrativa

Después del hero:

> **Pero esto no empezó acá.**

La web debe “ir hacia atrás”.

Ejemplo:

### 30 días antes
Invitación enviada.

### 20 días antes
127 confirmados.

### 12 días antes
Restricciones detectadas.

### 7 días antes
Grupos completos.

### 2 días antes
Pagos y accesos resueltos.

### Esa noche
Todo listo.

La sección debe explicar Alista sin necesidad de una definición abstracta.

---

# 11. La web como demo

## DECISIÓN

La web debe demostrar Alista, no solo describirla.

Antes del segundo o tercer viewport el usuario debería haber visto:

- una fiesta real;
- una invitación;
- una confirmación;
- algún elemento de producto funcionando.

---

# 12. Demo interactiva de invitación

Mostrar un teléfono realista dentro de la web.

Ejemplo:

> **Dharma te invita a sus 15**

Botón:

> **Abrir invitación**

Luego:

> ¿Venís?

Sí.

> ¿Quiénes vienen?

**Familia Pérez**
- María
- Tomás
- Juana

> ¿Alguna necesidad alimentaria?

...

Confirmar.

La interacción debe ser breve.

---

# 13. Mostrar “el otro lado”

Después de la confirmación, la web debe mostrar cómo Alista transforma esa interacción en información útil.

Ejemplo:

**Familia Pérez**

✓ Confirmados: 3  
Acceso: Cena  
Restricción: 1 vegetariano  
Invitación: enviada  
QR: listo

Mensaje:

> **Cada confirmación prepara mejor la llegada.**

---

# 14. Grupo como concepto visible

La web debe demostrar que Alista entiende familias y grupos.

No mostrar tres QR individuales como experiencia principal.

Ejemplo visual:

> **Familia Pérez · 3 personas**

Una invitación.

Una confirmación.

Un QR operativo.

Ingreso grupal.

Mensaje:

> **Llegan juntos. Entran juntos.**

---

# 15. WhatsApp como parte de la experiencia

## DECISIÓN CERRADA

Alista no reemplaza al remitente personal de la invitación.

La web debe mostrar:

> **La invitación sale de quien tiene que salir.**

Ejemplo:

**Dharma → WhatsApp → Martina → Alista**

Alista:

- prepara;
- personaliza;
- organiza;
- genera link;
- da seguimiento.

Pero el mensaje puede salir desde el WhatsApp personal de la quinceañera o del adulto correspondiente.

---

# 16. Copy para WhatsApp

Posible sección:

## La invitación no tiene por qué llegar de un número desconocido.

> Alista prepara cada invitación para que la mandes desde tu propio WhatsApp.

Visual:

- mensaje de Dharma;
- contacto conocido;
- preview de invitación;
- botón “Abrir WhatsApp”.

Esto debe transmitirse como una ventaja humana, no como una limitación técnica.

---

# 17. Recorrido del producto

No presentar una grilla de features.

Presentar situaciones.

## 17.1 Invitá

> Tu fiesta ya tiene identidad. La invitación también.

## 17.2 Confirmá

> Cada invitado responde solo lo necesario.

## 17.3 Conocé

> Antes de preguntar quién llegó, sabé quién viene.

## 17.4 Prepará

> Lo pendiente aparece antes de convertirse en problema.

## 17.5 Cobrá

> Si tu fiesta tiene entrada, cada pago queda asociado al acceso.

## 17.6 Recibí

> Cuando llega la noche, tu equipo ya sabe qué hacer.

---

# 18. Tipos de acceso

Alista incluye inicialmente tres tipos plantillados:

- Cena
- Trasnoche
- Trasnoche con entrada

Se puede agregar otros.

En la web deben aparecer como ejemplo de especialización.

Copy sugerido:

> **Cena, trasnoche o entrada paga. Alista ya entiende cómo funciona la mayoría de los 15. Y si tu fiesta es distinta, podés crear tu propio acceso.**

No convertir esto en una explicación técnica extensa.

---

# 19. Pagos

## Mensaje comercial

No usar:

> Pagos integrados.

Usar algo más cercano al problema real:

> **Cobrá las entradas sin perseguir comprobantes.**

## Explicación

> Cada pago se procesa por Mercado Pago y se acredita directamente en la cuenta que conectaste. Alista registra quién pagó y habilita su acceso.

## Secuencia visual

Pendiente  
↓  
Pago aprobado  
↓  
QR activo

---

# 20. Mercado Pago

No mostrar lenguaje técnico como:

- OAuth;
- marketplace;
- access token;
- API.

La experiencia debe verse como:

> **Conectar Mercado Pago**

Estado:

> ✓ Cuenta conectada

Mensaje:

> Tus cobros van directo a tu cuenta.

---

# 21. Centro de Preparación

## PROTAGONISTA DE PRODUCTO

Esta sección debe ser una de las principales demostraciones de valor.

Headline:

> **¿Está todo listo?**

Visual:

### Preparación del evento
92%

- 163 confirmados
- 2 pagos pendientes
- 3 grupos incompletos
- 1 restricción para revisar
- Mercado Pago conectado ✓
- QR generados ✓
- Recepción preparada ✓

Cada pendiente debe sentirse accionable.

Mensaje:

> **Alista transforma lo que falta en algo que podés resolver antes.**

---

# 22. No usar dashboards decorativos

Evitar:

- gráficos circulares sin propósito;
- KPI genéricos;
- charts empresariales;
- números sin acción.

El dashboard debe responder:

- qué falta;
- qué cambió;
- qué necesita atención;
- qué está listo.

---

# 23. Sección “Necesita tu atención”

Mostrar ejemplos:

> 17 grupos todavía no confirmaron.

> 2 pagos siguen pendientes.

> Martina agregó una restricción.

> Un acompañante cambió.

Cada uno con una acción.

Esto comunica que Alista no es una base de datos pasiva.

# 29. Check-in

Resultado:

✓ María  
✓ Tomás  
✓ Juana

> **Una familia no debería mostrar tres QR para entrar junta.**

# 30. Modo recepción

Mostrar que la operación prioriza:

- scan;
- búsqueda;
- velocidad;
- estado claro;
- grupo;
- pago;
- historial.

No mostrar un dashboard complejo en recepción.

---

# 31. Caso real

## Dharma

Debe existir una sección de caso real.

Usar solo métricas comprobables.

Ejemplos posibles:

- invitados cargados;
- confirmaciones;
- entradas vendidas;
- accesos registrados;
- tiempo de operación;
- cantidad de operadores.

No inventar cifras.

Mensaje:

> **Alista ya está pasando.**

El caso real tiene más valor que testimonios genéricos en esta etapa.

# 33. Argumento B2B2C

Una frase comercial muy potente:

> **Todos nuestros 15 incluyen Alista.**

La web debe mostrar cómo un salón/planner puede incorporar Alista a su propio servicio.

---

# 34. Modelo comercial

Por ahora la web debe estar preparada para:

## Familia

Pago por evento.

## Profesionales

Packs / condiciones comerciales por volumen.

No construir todavía pricing basado en:

- seats;
- usuarios;
- planes SaaS complejos.

La página de precios se definirá cuando se cierre el pricing final.

---

# 35. Trial / entrada al producto

La web debe poder evolucionar hacia:

> **Creá tus 15. Pagás cuando estés lista para publicar.**

Flujo deseado:

1. nombre;
2. fecha;
3. identidad;
4. invitación;
5. preview;
6. prueba;
7. publicación;
8. pago de Alista.

No obligar al usuario a pagar antes de entender el producto.

# 38. Mobile first

## DECISIÓN

La web debe diseñarse mobile-first de verdad.

Motivos:

- invitaciones llegan por WhatsApp;
- confirmaciones ocurren en teléfono;
- adolescentes navegan desde móvil;
- familias también;
- el producto invitado es principalmente móvil.

La experiencia debe sentirse cercana a una app.

---

# 39. Motion

Usar motion para:

- continuidad;
- anticipación;
- transformación;
- revelar preparación;
- conectar antes/después.

Evitar:

- animación gratuita;
- scroll hijacking;
- exceso de efectos;
- interacción que dificulte lectura.

---

# 40. Performance

Impacto no significa peso.

Priorizar:

- video optimizado;
- poster inmediato;
- lazy load;
- imágenes responsivas;
- motion progresivo;
- fallback;
- Core Web Vitals;
- carga rápida en 4G.

No usar WebGL/3D pesado sin una razón extraordinaria.

---

# 41. UI del producto dentro de la web

El producto mostrado debe ser real o muy cercano al producto real.

Evitar mockups que prometan features inexistentes.

La web puede anticipar features próximas solo si se identifican claramente como:

- próximo;
- en desarrollo;
- conceptual.

No vender humo.

---

# 42. Copy: reglas

El copy debe ser:

- corto;
- concreto;
- humano;
- seguro;
- contemporáneo.

Evitar:

- “revolucioná”;
- “transformá para siempre”;
- “la plataforma definitiva”;
- “experiencia 360”;
- jerga SaaS;
- marketing inflado.

---

# 43. Lenguaje propio del vertical

La web puede hablar naturalmente de:

- tus 15;
- cena;
- trasnoche;
- invitados;
- familia;
- amigas/os;
- confirmaciones;
- entradas;
- llegada;
- fiesta;
- esa noche.

Esto es una ventaja, no una limitación.

---

# 44. Qué NO debe hacer la nueva web

No debe:

- intentar demostrar que sirve para todos los eventos;
- mostrar veinte features por sección;
- usar QR como símbolo principal;
- parecer software de control;
- usar seguridad/vigilancia como territorio;
- usar estética princesa/cotillón como identidad fija;
- construir una landing SaaS genérica;
- esconder el producto;
- esconder que está especializada en 15;
- hablar solo a la quinceañera;
- hablar solo a la madre;
- hablar solo al planner.

---

# 45. Métricas de éxito de la web

Medir al menos:

- CTR hero → CTA;
- inicio de creación de evento;
- finalización de demo;
- interés B2B;
- solicitudes de demo;
- contacto WhatsApp;
- conversión a evento creado;
- conversión a evento publicado;
- scroll depth;
- interacción con demos;
- abandono por sección.

La web debe aprender del uso.

---

# 46. Principio maestro de UX/UI

> **No mostrar una lista de funcionalidades. Mostrar cómo se vive una fiesta mejor preparada.**

---

# 47. Principio maestro de venta

> **La web debe sentirse primero como parte del mundo de los 15 y, mientras la recorrés, demostrar que detrás hay una herramienta operativa muy seria.**

---

# 48. Síntesis

La nueva web debe ser simultáneamente:

- campaña;
- demo;
- caso real;
- pieza de marca;
- vendedor;
- puerta de entrada al producto.

No debe explicar Alista durante tres minutos.

Debe permitir que el usuario **experimente Alista durante tres minutos**.

> **La fiesta dura una noche.  
> Alista todo lo que pasa antes.**
